# Тестийн сахилга — Red · Green · Refactor (TDD)

Энэ төслийн **бүх шинэ feature, бүх bug fix** доорх гурван шатны мөчлөгөөр явна.
Тестгүй код merge хийхгүй.

## Гурван шат

**1. RED — Унасан тестээ эхлээд бич.**
Хийх гэж буй зан төлөвөө нэг жижиг тестээр илэрхийл. Ажиллуул — **заавал унасан байх ёстой**,
тэгэхгүй бол тест чинь юу ч шалгахгүй байна гэсэн үг. Унасан шалтгаан нь тохиргооны алдаа биш,
логик байхгүйгээс болсныг нүдээрээ батал.

**2. GREEN — Хамгийн бага кодоор ногоон болго.**
Зөвхөн тэр тестийг давуулах хамгийн энгийн кодыг бич. Ирээдүйг бүү таамагла.
Бүх тест ногоон болтол зогсохгүй.

**3. REFACTOR — Ногооноо хадгалж байж цэвэрлэ.**
Нэршил, давхардал, бүтэц. Өөрчлөлт бүрийн дараа тестээ дахин гүйлгэ —
улаан болбол шууд буцаа.

## Хатуу дүрмүүд

- **Нэг тест → уна → нэг засвар → нога.** Олон тестийг цувуулж бичээд дараа нь кодлохыг хориглоно.
- **Унаж буй кодыг давуулахын тулд тестийг өөрчлөхийг хориглоно.** Тест зөвхөн шаардлага
  өөрчлөгдсөн үед л өөрчлөгдөнө.
- Тооцооны дүрэм бүр (цикл, пропорц, алданги, хуваарилалт) **бодит тоон жишээтэй**
  тесттэй байна — жишээ нь Блүүмийн 306ш × 330₮ × 1 хоног = 100,980₮ кейс.
- Bug олдвол эхлээд түүнийг давтдаг унасан тест бич, дараа нь зас
  (жишээ: `test_auto_numbering_never_collides` — дугаарлалтын мөргөлдөөний регресс).

## TDD-ээр хийгдсэн жишээ (энэ repo-д)

`test_prepaid_credit_auto_applied_to_new_invoice`:
урьдчилж төлсөн мөнгө дараагийн нэхэмжлэл үүсэхэд автоматаар хаагддаггүй **цоорхойг**
эхлээд унасан тестээр баталж (RED), `apply_client_credit` implement хийж (GREEN),
дараа нь `allocate_payment`-тай логикийг `_fill_invoices`-д нэгтгэсэн (REFACTOR).
Frontend талд `allocationPreview` мөн адил: тест эхэлж унаад, функц дараа нь төрсөн.

## Үе 2-т мөрдөх журам

Бартер, Механизм, Зээл/өглөг, Цалин, Тайлан — модуль бүр:
1. Бизнес дүрмээ бодит тоон жишээ болгож тестэд буулгана (RED)
2. Хөдөлгүүрийг нь бичнэ (GREEN)
3. Цэвэрлэнэ (REFACTOR)
4. API + UI холбоно, characterization тест нэмнэ
